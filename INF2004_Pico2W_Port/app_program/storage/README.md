# v0.8.0 SD evidence and investigation logs

The storage profile adds a writer to the existing detection pipeline. Think of
an evidence slot as a tray: analysis fills it with four frames and their model
inputs, then sends small copies to the SD task. The tray becomes reusable only
when the SD task confirms that both the new evidence file and investigation
log were synced and closed.

This is incident recording. It does not record every Ethernet packet. The
existing policy still creates one incident per stream identity per boot, with
five ledger entries and two evidence trays. GOOSE and SV both use this path.
Successful storage frees evidence capacity; it does not clear the alarm or
reset the incident ledger. Failed evidence stays in RAM without automatic
retry during that boot. Analysis continues when the card is absent/full/failing.

## Compact original IRT logs

The user selected **direct onboard `.LOG` plus preserved `.BIN` evidence**.
Each new incident now creates a matching pair, for example:

```text
IECLOG/I0000003.LOG   compact IRTLOG/1 investigation summary
IECLOG/I0000003.BIN   exact four packets, metadata and full model input vector
```

The log keeps source/destination MAC, APPID/stream identity, boot-relative times,
packet sequence and length, GOOSE stNum/sqNum/first boolean or SV smpCnt/six values,
model verdict/score/threshold, shadow-rule findings, device ID, writer firmware,
model source SHA256/schema and the BIN filename/size/SHA256. It omits repeated
identity lines, raw hex dumps, full feature lists, startup messages and kernel/
stack/queue/performance telemetry. Identity is repeated only if it changes.
Numbers in the summary use six significant digits; exact bits remain in BIN.
Raw packets exclude Ethernet FCS. SV engineering units are not configured, and
UTC is unavailable; those facts are explicit rather than invented.
Incident IDs are scoped to one boot. Preserve the filename and digest when
correlating records. A model anomaly is not a confirmed attack, and an
unconfigured-stream rule finding is not an attack type. SHA256 identifies file
bytes; it is not a digital signature or proof of origin.

S1 first syncs/closes BIN, reopens it read-only, hashes/reads it in bounded
buffers, then creates/syncs/closes its LOG. `durable` and evidence release now
mean the **whole pair** completed. A log failure retains evidence and counts a
failed incident even if BIN already exists; partial new files remain available
for inspection. There is no automatic retry of that incident during the boot.
The next candidate name skips either an existing BIN or an existing LOG.
Existing incident/NOOBS files are never opened for replacement and no extra task/queue is added.

The native formatter is stateless with respect to libc: no printf/snprintf,
heap, TLS or additional DMA/IRQ ownership. Its SHA256 implementation uses a
16-word rolling schedule. FAT16 simulation checks complete pairs, preserved
files and BIN-only/LOG-only name collisions, plus retained evidence on failed
BIN/LOG sync or early write. Hash checks cover empty/padding boundaries and
multi-block data against independent Python/hashlib digests. Actual user BINs
also produce valid compact previews whose digests match their exact bytes.

Previews under workspace `IECLOG/irt-preview/` are generated by the SAME C
formatter through a memory FAT16 card. Old BINs do not store device/firmware
identity, so previews explicitly show `device=unrecorded` and
`writer_firmware=host-preview`; they are not claimed to be onboard dev3 output.
Dev3 embeds the actual device ID/current writer firmware and model-source hash.
Build/host checks pass. Dev3 now also has a successful mixed board run:
`durable=2 failed=0`, zero SD errors/timeouts and both evidence slots released.
That confirms paired sync/close/ACK execution; the actual new LOG contents and
hashes still await PC readback. Observed S1 stack use is852/2048bytes.
`backpressure=175` means retried chunks, not dropped records; `bytes=2504`
counts BIN payload only and excludes the LOG companions.
The earlier dev2 BIN feature/readback milestone remains passed.

### First functional use

Insert the existing FAT16/FAT32 card in the onboard slot, flash the enabled
storage UF2, then use the usual GOOSE or SV sender. A healthy mount reports
`SD state=2 pins=1`. After the first incident completes, `durable` increases
and `EVID released` increases. An absent/unusable card reports `state=3` and
an error; detection continues. States:0 disabled,1 waiting,2 ready,3 error.

A completed incident appears under `IECLOG` as matching new
`Ixxxxxxx.BIN` and `Ixxxxxxx.LOG` files.
Before taking the card out to read it on the PC, wait for `durable` to increase
and power the board off. Existing files are never deliberately replaced; the
writer may leave a partial new file after an error. Failed evidence stays in
RAM for that boot. No extra stall/soak test sequence is required for this step.

## Memory and task ownership

The GP19 finalized storage build reserves **213844/216064 bytes**, leaving 2220 bytes.
Dev2 reserves213204bytes; the native log extension adds640bytes.
The rebuilt v0.7 profile also passes at 214992 bytes; its preserved board-tested
image remains available.
That includes static buffers, task stacks, the bounded libc heap and SDK exception
stacks. The storage profile removes only the 5176-byte marked UDP test tracker;
v0.7 retains it. Capture buffers, model inputs, stream histories, SV samples and
all four raw evidence frames retain their capacities. The filesystem shares one
512-byte sector buffer; there is no second whole-record staging buffer or heap
allocation. This reservation check does not establish hardware stack peaks.

S3 (the Core0 consumer) owns evidence allocation/release and serializes one chunk
without waiting. S1 (Core0 priority18, 2048-byte stack) owns FatFs/card operations.
The two-entry copied data queue holds 256-byte payloads; a separate two-entry
queue carries completion acknowledgements. Together with capture/alarm, these
use the configured four message buffers. Higher-priority analysis, alarm and
supervision can run while S1 waits for card programming.

Actual excerpt from `storage.c`, `storage_poll` (not a standalone source file):

```c
if (E_OK == tk_snd_mbf(g_chunks, &chunk, sizeof(chunk), TMO_POL))
{
    g_offset += chunk.length;
}
else
{
    gb_waiting_ack = false;
    g_backpressure++;
}
```

`TMO_POL` means “try now”: a full queue delays storage instead of blocking
analysis. A success acknowledgement must match both evidence slot and incident
ID, and arrive after the final chunk. Failure acknowledgements may arrive early
and retain the evidence. S1 never receives a pointer to reusable capture memory.

## Files and existing card contents

FAT16/FAT32 are supported. The writer creates `IECLOG` if absent, then creates
exclusive files such as `IECLOG/I0000000.BIN`. Existing names are skipped, with
at most 64 collision attempts per record. No format, trim, delete, append or
truncate operation is exposed. Existing NOOBS files are not replaced. Failed
writes may leave a partial **new** incident file for inspection. Filesystem
metadata still changes when new files/directories are created; FAT is not a
power-loss journal.

Actual excerpt from `storage_file.c`, `storage_file_begin`:

```c
result = f_open(&g_file, g_name, FA_WRITE | FA_CREATE_NEW);
```

`FA_CREATE_NEW` fails if the name already exists. Completion requires both
`f_sync` and `f_close` to succeed, including the disk driver's card-ready check.
Dev3 additionally requires completion of the LOG companion.
This confirms completion through the software/card interface; it does not claim
power-loss recovery qualification.

The binary format starts with `P2INC001`, version1, and uses explicit little-endian
fields, not raw C structs. Its 48-byte header records total size, incident ID,
protocol (0 GOOSE,1 SV), boot-relative microsecond timestamp, frame/feature counts,
label, float32 probability and rule reasons. Next come all 52/72 float32 model
inputs. Each of four frames has a 132-byte metadata header (length, APPID,
sequence, timestamp, counters, stream key, MACs, stream identity and six value
words) followed by its exact raw bytes. A partial/trailing-length mismatch is
rejected by the reader.

Read a copied file on the PC:

```powershell
python -B .\testing\storage\read_incident.py D:\IECLOG\I0000000.BIN
```

The reader defaults to JSON with metadata, features, value bits and raw frame hex.
For a human-readable companion log (created on the PC):

```powershell
python -B .\testing\storage\read_incident.py D:\IECLOG\I0000001.BIN --format text --output I0000001.txt
```

Text includes protocol/stream, uptime, MACs, counters, GOOSE boolean or SV floats,
model label/score, named features and a raw-packet hex appendix. `--output`
creates a new file and refuses to replace any existing file. The original BIN
is never modified. This verbose `--format text` report is still a PC conversion. Dev3 also writes
the much smaller original `.LOG` summary directly on the card.

The supplied files have readable TXT and JSON companions in the workspace's
`IECLOG/readable/` directory. `I0000000` matches the earlier GOOSE incident;
`I0000001` and `I0000002` match the latest mixed GOOSE/SV run.
Timestamps are uptime, not a wall-clock date; filesystem dates use the fixed
1980 placeholder because this profile has no RTC synchronization.

## Focused verification and provenance

`testing/host/run_storage_tests.ps1` runs the real FatFs, serializer, storage
queues and evidence-release code against a memory FAT16 card. It checks CRC
fixtures, chunk parity, saved content, preserved existing files/name collisions,
invalid ACKs, and retained evidence on sync/early-write failure. The real SD
driver also runs against a register/API model that injects scheduling gaps
before/after FIFO checks and DMA completion, plus genuine stuck-device cases. This sends no
network traffic and accesses no physical card. Existing host regression checks,
target software-math verification and RAM reservation check also pass.

Filesystem: [ChaN FatFs R0.16](https://elm-chan.org/fsw/ff/) with
[official patch1](https://elm-chan.org/fsw/ff/patch/ff16p1.diff). Its license and
source notices are retained in `third_party/fatfs`; `provenance.json` records
archive/patch/source hashes. FatFs uses tiny mode, short filenames and one owner,
with formatting, exFAT, long filenames and dynamic allocation disabled. As with
the existing project dependencies, `third_party/` and `testing/` remain ignored
under the user's sharing policy; a fresh Git clone lacks those local files.
